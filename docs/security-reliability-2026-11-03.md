## Transaction boundary

`withStorageLock` uses native Web Locks named by the existing storage key plus IndexedDB checkpoints in `japan-travel-write-checkpoints-v1` / `snapshots`. The checkpoint stores only the latest raw value for each key; it is browser-local private data, not telemetry. WebKit could still silently lose an update with Web Locks alone; task-turn waits were experimentally insufficient and were removed. A mismatched local cache now fails with an explicit conflict before mutation. Trip changes, Undo and reset acquire the trip lock before reading current storage, checking expectations, validating and writing. Saved-copy writes use the library lock; data erasure acquires trip then library in that fixed order. Successful history/feedback effects are deferred until the checkpoint write completes. Checkpoint failure rolls back the local mirror before returning failure; explicit erasure writes null checkpoint payloads. Pending writes and drafts trigger the existing unload warning. Keys, version-1 schemas, place aliases and recovery formats remain unchanged.

Callers await successful persistence before moving focus, clearing personal/FX drafts or closing an import preview. A focused field captures its edit group when an operation starts. Queued keystrokes may follow a snapshot observed at entry only when actual storage still equals that group's own last commit; external interleaving remains a conflict. There is no general stale-snapshot bypass.

Pending field text is immediately retained in the existing session draft store. Abort signals cancel superseded/discarded/unmounted queued edits; operation sequences stop older results clearing newer text. Discarding a draft is also checked inside the trip transaction. Mutation controls wait while writes are pending; text fields remain editable so newer keystrokes can replace queued text. A checklist holds its pending checkbox state until the transaction settles. Successful messages are emitted after persistence. Draft and error notices share a measured, scrollable stack so a persistent error cannot cover recovery controls.

Web Locks and IndexedDB require an available supported browser and a secure context: HTTPS or localhost. Unsupported/denied saving fails without an unsafe unlocked fallback, preserving existing storage and recovery downloads. Reload older-release tabs before editing; mutual exclusion applies to cooperating current-release writers of the same origin. This is local coordination, not accounts, cloud synchronization or protection against another compromised same-origin script.

The localStorage mirror and IndexedDB checkpoint are separate browser APIs, not a fully atomic crash-recovery database. An abrupt process termination between them, or an older/uncoordinated writer, can leave a persistent mismatch. The app fails closed instead of guessing which private data to overwrite. Keep a JSON backup; if reloading cannot resolve a mismatch, export the available raw data, explicitly reset/erase, then restore the reviewed backup. Erasure across multiple keys can also be partial if the browser denies a later operation; success is not reported on that failure.

Tests seed both the mirror and checkpoint through a fixture helper and read committed checkpoints using a shared read lock. Fault simulations deliberately leave a stale cache uncoordinated and require rejection; fresh reload/raw reads independently verify the mirror. Existing equality/integrity assertions remain; the fixture waits behind actual transactions rather than sleeping or retrying writes. The old no-draft-write expectation intentionally changes: pending async edits now write a draft before commit and clear it afterwards. New tests separately observe uncommitted storage while deliberately holding a lock, exercise native concurrent saves, stale Undo, queued discard, rapid typing and missing Web Locks.

## Security checks

The deployment checker parses directive names and token lists, rejects duplicate directives, requires exact values for its four mandatory restrictions and disallows unsafe-eval. Negative self-tests cover broader defaults, ambiguous none values, duplicated directives, missing restrictions and unsafe-eval; the real Next configuration remains accepted. The application CSP itself is unchanged. This closes a checker false-positive, not a claim of an exploited deployed policy.
