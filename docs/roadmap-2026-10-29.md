# Development direction and reliability — 2026-10-29

The next goal is to help a first-time visitor choose a place, understand its approach, keep a reliable plan and use it while traveling. Preserve the Japanese minimal visual identity, day/night themes and on-demand miniature. Prioritize task completion, verified detail and measured loading cost over another visual overhaul.

This proposal was reviewed by five specialist agents and the integration lead against HEAD `f4686da`. The user then authorized a first implementation batch. Evidence below distinguishes source findings from ideas that still need observation, prototypes or deployment measurements.

## Authorized first batch

1. **Lodging removal safety.** The old handler used a rendered array index while applying an update to current storage. Remove by stable stay ID and require the expected snapshot, so a concurrent edit cannot delete another stay. Test a stale row, successful removal and Undo.
2. **Follow a reassigned visit.** After a successful day change, reveal the destination when filtering and focus its day heading after React commits. Announce the place/day using existing localized text. Repeated visits keep their entry identity; failed writes must preserve view/focus and all scheduling metadata.
3. **Checkout-day origins.** Offer both the hotel being checked out of and accommodation for the coming night on a changeover day. Distinguish their labels in all three languages. Keep nightly stay summaries and night counts unchanged; Google Maps uses the selected address.
4. **Useful map-sheet detail.** Place a compact entrance/accessibility disclosure before the route link, reusing existing facts, unknown labels and per-field sources/dates. Preserve the full details view. Remove the duplicate record-wide review date rather than imply it verifies every field.
5. **Reliable quality evidence.** Run dependency audit and scheduled/manual source checks before UI tests. Expand Firefox to the existing refinement, draft/FX, trip-safety and saved-place suites, plus the new reliability cases; do not run every visual reference on every engine or add retries to conceal errors.

Day selection currently has separate planning and travel-day state. This is not automatically a bug: today's travel view may legitimately differ from a future planning day. Observe the task and agree on wording/transition behavior before unifying state. The compact header and fewer miniature controls are similarly prototype candidates, not proven defects.

## Performance and scope gates

Use production baselines at a pinned commit and consistent viewport, network/CPU profile and cache state. Inspect direct loads and client navigation. CSS coverage must include interactive states; unused-on-first-load does not mean safe to delete. Use [Chrome's Coverage guidance](https://developer.chrome.com/docs/devtools/coverage) to support the experiment.

For field data, target p75 LCP at most 2.5s, INP at most 200ms and CLS at most 0.1, assessed separately for mobile and desktop as described by [Web Vitals](https://web.dev/articles/vitals). Lab runs guide diagnosis; they do not establish production field scores. Keyboard changes should preserve meaningful navigation, consistent with [W3C Focus Order guidance](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html).

Keep the current three languages, reference-map fallback, file-based backup and static/local-storage architecture while validating these improvements. A fourth language multiplies editorial maintenance. Accounts/cloud sync, PWA caching, paid map services, AI itinerary generation and additional 3D libraries require a demonstrated visitor need and operating/privacy design; they are not prerequisites for a modern, useful guide.

This batch does not add visitor analytics, verify live hosting settings or claim that native-language review, field routes, real-device performance and novice sessions have been completed. The pre-existing `next-env.d.ts` development references remain outside the release.

The five new reliability cases passed in Chromium, mobile WebKit and Firefox. Existing visual baselines passed unchanged.

The integration lead inspected the expanded map disclosure at 390px in English, Japanese and Thai. The dialog remains vertically scrollable with no horizontal content overflow. Native select End/Home automation behaved differently across desktop engines, so the regression uses deterministic native selection events and verifies actual post-commit focus and failed-write behavior. Real OS picker keyboard behavior remains a physical/manual acceptance item.

No visitor facts, source dates, stable IDs, storage schema, dependencies or CSS were changed. The conflict message now explains general saved-value conflicts as well as reopening an import preview. The workflow on the release commit supplies Linux verification; the source-check job runs only on its existing scheduled/manual events.
